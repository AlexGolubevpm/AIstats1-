# 06. Метрики

Все формулы считаются **из сумм**, а не как среднее средних: `SUM(revenue) / SUM(page_loads) × 1000`, а не `AVG(rev_per_k)`. Деление на ноль даёт `NULL`, в UI — `—`. Реализация — единственный модуль `src/lib/metrics.ts` плюс SQL-вьюхи; оба покрыты тестами на одинаковых фикстурах.

## Грануляция источников

| Источник | Минимальный разрез | Что даёт |
| --- | --- | --- |
| AdSpyglass, гео | дата × сайт × сетка × страна × девайс | page loads, показы свои и сетки, клики, выручка. Включает own deals |
| AdSpyglass, зоны | дата × сайт × зона × формат | то же + видимые показы. Own deals не входят |
| Метрика | дата × сайт × страна × девайс | уники, просмотры, визиты, отказы, глубина |
| Закупка | дата × сайт × страна × источник | купленные уники, ставка, расход |
| Фикс-дилы | дата × дил × сайт × страна | загрузки, свои показы, показы рекламодателя, выручка, статус |

Общий знаменатель всех источников — **дата × сайт × страна**. ROMI существует только на нём и выше.

## Базовые метрики

| Метрика | Формула | Формат | Где применяется |
| --- | --- | --- | --- |
| Выручка | `revenue_mediated + revenue_direct` | money | Везде |
| Расход | `SUM(cost)` | money | Сайт × гео и выше. По странам — оценка: расход без страны (`ZZ`) разложен по загрузкам ([ADR 0008](../adr/0008-forecast-and-geo-cost-allocation.md)) |
| Маржа | `revenue − cost` | money, цвет | Сайт × гео и выше — **до** операционных расходов (KPI сводки, таблицы сайтов, бандлов, гео, вьюхи, MCP `margin`). **После** них (`revenue − cost − opex`, [ADR 0007](../adr/0007-opex-and-calendar-months.md)) — на `/finance`, в P&L-графике сводки, на `/forecast` и в MCP `margin_after_opex`; там это подписано |
| Опер. расходы | `SUM(v_opex_daily.amount)` — цифра месяца / дней в месяце, по дням | money | `/finance`: KPI, таблица по месяцам, P&L (расход сети — по сайтам пропорционально выручке) |
| **ROMI** | `(revenue − cost) / cost × 100%` | percent, цвет | Главная цифра бандла и сайта. Всегда на расход на трафик, без опер. расходов |
| Уники | `SUM(uniques)` — сумма дневных | int | Подпись в UI: «сумма дневных уников» |
| RPM на уника | `revenue / uniques × 1000` | money | Сравнение сайтов и бандлов |
| **Rev / 1000 loads** | `revenue / page_loads × 1000` | cpm | Основная метрика сравнения сеток внутри гео |
| CPM | `revenue / imps_own × 1000` | cpm | Только внутри одного формата |
| Viewable CPM | `revenue / views × 1000` | cpm | BANNER, NATIVE |
| View rate | `views / imps_own` | percent | BANNER, NATIVE. < 15% — проблема вёрстки |
| Fill rate | `imps_own / page_loads` | percent | Сколько запросов закрылось |
| Дискрепанси | `(imps_own − imps_network) / imps_own` | percent | Отрицательная — рекламодатель насчитал больше |
| Множитель дила | `imps_reported / imps_own` | ×1.00 | Фикс-дилы, > 1.5× — предупреждение |
| Cost / unique | `cost / uniques_bought` | cpm (4 знака) | Цена входа |
| Глубина | `pageviews / uniques` | 0.00 | Множитель между ценой уника и показами |
| Доля в выручке | `revenue / SUM(revenue) по разрезу` | share | Зоны, форматы, сетки — вместо ROMI |
| Доля объёма | `page_loads / SUM(page_loads) по site × country` | share | Сетки |
| Ранг по цене | `RANK() по rev_per_1k_loads DESC внутри site × country` | int | Сетки |
| Эффективный CPM дила | `revenue_confirmed / imps_own × 1000` | cpm | Карточка дила |
| Подтверждённая доля | `revenue_confirmed / revenue` | percent | `/finance` |

**rCPM в интерфейс не выводим.** Он считается на свои показы и завышает источники с низким филом. Для сравнения источников — только rev / 1000 loads.

**ROMI в разрезах без расхода** (зоны, форматы, сетки) не определён: на его месте стоит доля в выручке.

## Дельты

- Сравнение с предыдущим равным периодом: 7 дней против предыдущих 7.
- Для денежных и счётных метрик — дельта в процентах.
- Для процентных (ROMI, fill rate, view rate) — дельта в **процентных пунктах**.
- Если база сравнения равна нулю, дельта не показывается.

## Пороги подсветки

| Где | Правило |
| --- | --- |
| Заливка ROMI и маржи в таблицах | Только при отклонении > 20% от среднего по разрезу; ниже нуля — всегда красная |
| Дискрепанси | до ±10% нейтрально · ±10–25% `--warning` · дальше `--negative` |
| View rate | < 15% — бейдж «не видна» |
| Доля зоны | < 1% выручки — бейдж «кандидат на снос» |
| Множитель дила | > 1.5× — `--warning` |
| Свежесть ингеста | > 2 ч — жёлтая точка, failed — красная |

<a id="alerts"></a>
## Алерты

Считаются SQL-правилами ночью (`derive`, 04:45 UTC) и при старте воркера, складываются в таблицу `Alert`. Ключ алерта — `rule + entity`; повторное срабатывание обновляет существующий, а не создаёт новый. Каждое правило отдаёт **действие** отдельным полем (`payload.action`) — его показывают «Рекомендации»; сообщение — только «почему». Все правила пропускают архивные сайты; правила по данным (1–6) смотрят только дни до сегодняшнего, а если за вчера нет разреза по странам, их алерты не закрываются (нет данных ≠ всё хорошо).

| # | Правило | Условие | Уровень | Рекомендуемое действие |
| --- | --- | --- | --- | --- |
| 1 | Убыточное гео | site × country за 7 дней: revenue < cost, cost > $5, ≥ 10 000 загрузок; только дни, когда у сайта есть разрез по странам; расход `ZZ` (источники) разложен по странам дня по загрузкам, как в таблице гео; `XX` не учитывается | critical | Снизить закупку гео или поднять флор |
| 2 | Инверсия waterfall | site × country за 7 дней: сетка с рангом по цене > 3 держит > 30% объёма, loads > 10 000. Ранг — только среди сеток с ≥ 5% загрузок; системные сетки (own deals, «все сетки») не участвуют | warning | Переставить сетку ниже, объём отдать сетке X |
| 3 | Аномальная дискрепанси | сетка × гео: \|дискрепанси\| > 25% два дня подряд при > 5 000 показов; системные сетки не участвуют. Отрицательная и множитель > 2× → critical | warning / critical | Сверить счётчики; перевести дил на оплату за загрузку |
| 4 | Невидимая зона | BANNER/NATIVE, view rate < 15% при > 50 000 показов за 7 дней; нужны реальные просмотры (без `banner_view_rate` от ADOK просмотров нет — правило молчит) и выручка > 0; «под риском» = выручка при view rate 35% (viewable CPM × показы × 0,35) − факт, не меньше $5; зоны, место которых занято дилом, не учитываются | warning | Поднять зону выше фолда или перенести на другое место |
| 5 | Мёртвая зона | за 30 дней < 1% выручки зон **того же формата** на сайте при > 5% их показов (CPM сравним только внутри формата); ≥ 50 000 показов, данные за последние 3 дня, зона активна, место не занято дилом; «под риском» = выручка по CPM формата − факт | warning | Снести, отдать место формату с высоким CPM |
| 6 | Низкий фил формата | fill rate < 25% при > 100 000 запросов за 7 дней | warning | Подключить бэкфилл |
| 7 | Дил без цифр | период биллинга закрыт больше 7 дней назад, данных рекламодателя нет | warning | Запросить отчёт у рекламодателя |
| 8 | Просроченная оплата | выставлено, срок оплаты прошёл, остаток к оплате > 0 | warning (> 30 дней — critical) | Напомнить рекламодателю |
| 9 | Ингест упал | последний `IngestRun` источника failed или старше 3 часов | critical | Открыть `/settings/integrations` |
| 10 | Фикс-дил заканчивается | активный или приостановленный дил с датой конца: осталось ≤ 7 дней; дата прошла, а дил всё ещё активен | warning при 4–7 днях; critical при ≤ 3 днях и после даты конца | Договориться о продлении (новая дата конца) или завершить дил и освободить место |

| 11 | Источник без подтверждённой доли | источник трафика, созданный из ADOK с долей расхода по умолчанию (100%), принёс сумму за 7 дней, а владелец долю не задавал (`CostSource.confirmed = false`) | warning | Задать долю расхода в Настройки → Расход (0% — бесплатный трафик) |

Правила 7–11 добавлены к спецификации для раздела фикс-дилов, надёжности ингеста и расхода по источникам.

**Этапы правила 10.** В `payload.stage` записывается порог: 7, 3, 1 или 0 (дата прошла). Смена этапа — новое уведомление: `firstSeenAt` сбрасывается на сегодня, снятое «принято к сведению» возвращается. Так один дил поднимается в алертах три раза — за неделю, за три дня и за день, — а не висит одной строкой. Деньги под риском — выручка дила за последние 30 дней. Дилы без даты конца правило не трогает.

<a id="forecast"></a>
## Прогноз месяца

`темп = Σ(метрика за последние N полных дней) / N`, где полный день — день до сегодняшнего с данными о выручке (день без данных пропускается, а не считается нулём); N = 3, 7 или 14 (по умолчанию 7), полных дней меньше N — берутся те, что есть. `прогноз месяца = факт с начала месяца + темп × дней впереди` (сегодняшний день — впереди). Темп считается отдельно для выручки и расхода на трафик; операционные расходы известны на каждый день месяца из `OpexEntry`; маржа прогноза = выручка − расход − опер. расходы; ROMI — на расход на трафик. Без сезонности по дням недели и без тренда — сознательно: при 27 сайтах и трёх днях данных любая модель сложнее среднего даёт ложную точность ([ADR 0008](../adr/0008-forecast-and-geo-cost-allocation.md)). Реализация — `src/lib/forecast.ts` (`projectMonth`), тесты на синтетике.

<a id="recommendations"></a>
## Рекомендации

Собираются на `/recommendations` из двух источников. Из **алертов** — действие правила (`payload.action`); у алертов, записанных до появления поля, — последнее предложение сообщения. Из **правил по таблицам** (`src/server/domain/recommendations.ts`):

| Область | Условие | Что сделать | Под риском |
| --- | --- | --- | --- |
| Сайт | за 7 дней расход на трафик > выручки (расход > 0) | Снизить закупку или поднять флор; проверить убыточные гео | −маржа |
| Зона | за 30 дней < 1% выручки зон того же формата на сайте при > 5% их показов, ≥ 50 000 показов | Снести или отдать место формату с более высоким CPM | — |
| Зона | BANNER/NATIVE, view rate < 15% при > 50 000 показов за 7 дней, просмотры и выручка > 0 | Поднять выше фолда или сменить место | — |
| Сетка | ниже флора сайта (флор > 0) и ≥ 10% объёма за 7 дней; флор печатается с 4 знаками | Поднять флор до X за 1000 загрузок или опустить в waterfall | (флор − rev/1k) × loads / 1000 |
| Источник | за 7 дней расход источника ≥ 60% выручки сайта и > $5 | Снизить закупку или договориться о доле; проверить, что сумма ADOK — расход | расход − 50% выручки |
| Формат | свободные места на сайте из топ-10 по выручке (выручка > 0) | Продать фикс-дил или включить ротацию | — |

Пороги правил по зонам равны порогам алертов №4 и №5 (невидимая: view rate < 15% при > 50 000 показов за 7 дней с просмотрами и выручкой; мёртвая: < 1% выручки зон того же формата при > 5% их показов за 30 дней, ≥ 50 000 показов) — между ночными прогонами правило лишь дублирует алерт. Про один объект алерт важнее правила: дедуп по ключу объекта (правило + id зоны / сайта / сетки). Сортировка: critical → warning → info, внутри — по сумме под риском.

## Рекомендация флора

Колонка в таблице сеток, не алерт. Считается **по сайту за выбранный период** (ADOK не отдаёт сетку × страну, а формат есть только у зон), а не по `site × country × format` за 14 дней, как в спецификации:

```
floor = rev_per_1k_loads лучшего источника × 0.4 + второго × 0.6
        (60-я точка между двумя лучшими источниками сайта за период)
```

Кандидаты во «флор» — только медиационные сетки с ≥ 5% загрузок: own deals (прямые), строка «AdSpyglass (все сетки)» (дни без разреза по сеткам) и сетка с горсткой загрузок флор не задают и бейдж «ниже флора» не получают.

Источник с rev / 1000 loads ниже флора получает бейдж «ниже флора»: он занимает слот в waterfall, не оплачивая его.

## Контрольные сверки (обязательные тесты данных)

- Выручка за день в дашборде сходится с кабинетом AdSpyglass в пределах ±2%.
- Сумма по сайтам бандла = итог бандла.
- Итог сети = сумма по сайтам, а не по бандлам.
- Own deals не задваиваются с медиацией.
- Сумма дневной раскладки фикс-дила = сумма периода до цента.
- Нераспознанных гео меньше 1% строк.
