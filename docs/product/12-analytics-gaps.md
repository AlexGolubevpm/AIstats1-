# 12. Чего не хватает для полного анализа тьюбов

Срез на 2026-10-03, после первой полной ночной выгрузки AdSpyglass (01–02.10: 27 сайтов, страны, сетки, устройства, источники трафика, зоны, расход). Документ — список дыр и нужных выгрузок, в порядке ценности. Что сделано — вычёркивается в том же PR, где закрывается.

## Что уже есть

| Разрез | Источник | Грануляция | Состояние |
| --- | --- | --- | --- |
| Выручка и загрузки по сайтам | ADOK `group_by=website` | день × сайт, каждый час | работает, сходится с ADOK до цента |

## Дыры, по убыванию ценности

### 1. История: данные только с 01.10

Разрезы по сайтам есть за два дня. Без сентября нет сравнения месяц к месяцу, трендов на сводке, дельт в алертах. Нужна джоба **`asg:backfill`**: тот же `asg:sites`, но за произвольное окно, порциями под дневной бюджет (27 сайтов × 4 запроса × 30 дней ≈ 3 240 запросов ≈ 7 ночей при бюджете 500). Запуск с «Интеграций» с полем «с какой даты», прогресс в `IngestRun`. **Это первое, что стоит сделать.**

### 2. Метрика: уников нет

Без `METRIKA_TOKEN` нет `FactTraffic`: уники, визиты, глубина, отказы, источники переходов по Метрике. Это закрывает RPM на уника, цену уника, глубину и «полноту» в P&L (сейчас у всех сайтов «нет Метрики»). ADOK даёт только загрузки (`hits`), не людей. Токен — в секрет `production`, дальше workflow `Sync server .env` ([CICD](../CICD.md)).

### 3. Расход по источникам — проверить одной накладной

Сейчас расход источника = сумма, которую ADOK называет его выручкой, × 100%. Если это действительно «сколько заплатили источнику», маржа сайта ≈ выручка Direct + organic + прямые дилы (по данным 01–02.10 расход = 88% выручки). Сверить **одну** реальную накладную TubeCrown или TubeTraffic за день/неделю с суммой в «Настройки → Расход» по тому же источнику. Если не совпадает — это выручка трафика источника, а расход надо грузить CSV-импортом или ставками (всё уже есть), и тогда появляется **ROMI по источнику** (выручка его трафика − его счёт). Пока поле понимается как расход, ROMI по источнику посчитать нельзя: нет выручки, которую он принёс.

### 4. Own deals по рекламодателям: разрез `campaign`

Дилы «через AdSpyglass» видны одной строкой сетки `own_deals`. ADOK отдаёт `group_by=campaign` (200, проверено) — по нему по каждому сайту можно получить выручку и показы каждой кампании/own deal. Нужно: ночью `campaign` + `platforms_ids[]` (+1 запрос на сайт в день, ≈ 27 в ночь) → `FactRevenueCampaign`; сопоставление кампании с `Deal` (поле `asgCampaignId` у дила) — тогда карточка VIA_ASG-дила показывает деньги и дискрепанси, а «Форматы» видят own deal по месту без ручной разметки.

### 5. Форматы напрямую из ADOK: разрез `ad_type`

Сейчас формат = `Zone.format` из названия и ручная привязка зон к местам. `group_by=ad_type` + `platforms_ids[]` даст выручку по типам (popunder, banner, native, in-video…) по сайту без зон — для сверки форматного разреза и для сайтов, где зоны не размечены. +1 запрос на сайт в день.

### 6. Зоны по сайту с фильтром

Зонный разрез берётся одним аккаунтным запросом и привязывается к сайту по домену в названии зоны. Поля сеток (`broker_income`) в нём не проверены на «фильтруемость» так же тщательно, как в странах. Стоит один раз сравнить (`MODE=recon` уже печатает зоны к итогу сайта) и, если расходится, брать `spot` + `platforms_ids[]` или раскладывать по `predicted_income`, как для стран.

### 7. Разрезы, которых в API нет

Страна × сетка, страна × устройство, сетка × формат — ADOK отвечает 422 на два измерения. Поэтому флор по сетке внутри страны и «какая сетка лучше в JP» считаются по оценке. Единственный путь — экспорт CSV из веб-интерфейса ADOK (там отчёт умеет два измерения) и импорт, либо просьба к ADOK открыть мульти-`group_by`. Пока — пометка «оценка» в UI остаётся.

### 8. Выручка аккаунта, не привязанная к сайтам

Аккаунтный разрез по сеткам больше суммы сайтов на ~7%. Это зоны/кампании без сайта или удалённые сайты. Нужна строка «Не привязано к сайтам» на сводке и в P&L (`asg_unknown_sites` уже копится в `AppSetting`), чтобы итог сети сходился с кабинетом ADOK, а не только с суммой сайтов.

### 9. Платформы и браузеры

`group_by=platform` (ОС), возможно `browser` — для диагностики падений (обновление iOS, блокировщики). Низкий приоритет: +1–2 запроса на сайт в день, ценность — только при расследованиях.

### 10. Что не из ADOK

- **Контент и SEO**: Ahrefs / Search Console (позиции, трафик по страницам) — отдельный контур, не для MVP.
- **Выплаты сеток**: ADOK платит одной суммой — уже учитывается в «Выплатах AdSpyglass». Выплат по сеткам отдельно нет и не нужно.
- **Курс валют**: всё в USD, пока источники и рекламодатели платят в USD.

## Аудит 2026-10-03: что берём, что игнорируем, где оценка

**Запросы.** Почасово `group_by=website` (1 запрос на день окна). Ночью по каждому сайту с `platforms_ids[]`: `country`, `adnetwork_squashed`, `device`, `traffic_source`; плюс `website` (эталон) и `spot` по аккаунту. Другие разрезы (`date`, `ad_type`, `platform`, `adnetwork_type`, `campaign`) не запрашиваются.

**Поля ADOK, которые храним:** `hits` → загрузки, `impressions` → свои показы, `broker_hits` → показы сеток, `clicks`, `broker_income` → выручка. Используем, но не храним: `predicted_income` (веса раскладки и сверка ±2%), `banner_view_rate` (только в зонах → видимые показы), `ad_type` (только в зонах). **Игнорируем:** `broker_clicks`, `fill_rate`, `requests`; `broker_hits` у источников трафика теряется (нет колонки). Сырые ответы лежат в S3 — любое поле можно досчитать задним числом, но перечитать умеем только `website`, `country`, `device`.

**Точно vs оценка.** Точные: итог сайта, сетки по сайту, источники трафика по сайту. Оценка: страны и устройства (выручка сеток раскладывается по `predicted_income`, [ADR 0005](../adr/0005-network-revenue-from-site-totals.md)); расход по странам (разложен по загрузкам, [ADR 0008](../adr/0008-forecast-and-geo-cost-allocation.md)). **Не сверено:** зоны берутся одним аккаунтным запросом и привязываются к сайту по домену в названии (`www.` и поддомены не совпадут), их `broker_income` с итогом сайта не сверяется; сверка ±2% есть только у стран и только по `predicted_income`.

**Окна.** Сегодня — только почасовой итог (без разрезов). Вчера после 04:00 UTC заморожено до следующей ночи (`ASG_RESTATE_DAYS=2` → каждый день читается ночью дважды, T+1 и T+2). Сайт без `adsgSiteId` разрезов не получает. Метрика не рестейтится дальше вчера.

**Исправлено этим аудитом:** догон при старте воркера (расход, алерты, дилы), алерты без «ZZ» как страны, дедуп рекомендаций по объекту, выплаты ADOK переживают переингест, own deals в ячейках «Форматов», полный день прогноза = день с данными ADOK, подписи «до/после опер. расходов», readiness без ложных FAIL по Метрике.

**Остаётся:** п. 1–9 выше; сверка зон с итогом сайта; хранить `predicted_income` (дискрепанси по выручке сетка vs ADOK); `broker_clicks`/`fill_rate` ADOK против наших.

## Бюджет запросов ADOK

Сейчас в ночь ≈ 220 (27 × 4 × 2 дня) + 48 почасовых. Пункты 4, 5, 9 добавляют по 54 запроса за ночь каждый; с бэкфиллом нужно 500–600 в день, лучше 800 (`ASG_DAILY_BUDGET`, интервал 5 с → 800 запросов ≈ 70 минут).

## Что сделать владельцу сейчас

1. Запустить `asg:sites` за сентябрь (пока нет `asg:backfill` — по несколько дней за раз, под бюджет), или дождаться джобы из п. 1.
2. Положить `METRIKA_TOKEN` в секреты и прогнать `Sync server .env`.
3. Привязать зоны к форматам на «Форматах» (кнопка «N зон без формата»).
4. Проверить доли источников в «Настройки → Расход» (Organic SE, No source — 0%) и сверить одну накладную (п. 3).
5. Внести операционные расходы за сентябрь и октябрь на `/finance`.
