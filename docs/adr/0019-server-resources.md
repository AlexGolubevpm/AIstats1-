# ADR 0019. Диск и память сервера: сжатие и срок хранения сырья, ротация логов, лимиты контейнеров

Статус: принято · 2026-10-26

## Контекст

На VPS (8 ГБ памяти) занято 50 ГБ диска, память периодически показывает 99%. Что растёт без ограничений:

- **Сырьё** (`raw_data`). Принцип 4 спецификации — сохранять ответ API до трансформации. Каждый прогон пишет свой файл (`…/{date}/{runId}.json`) и ничего не удаляется: почасовые итоги дают 24 копии дня, ночной прогон перечитывает 3 дня по всем разрезам. Читается при этом только последний прогон дня (`rawGeoKeys`, `siteTotalsFromRaw`) и не дальше 90 дней (`geo:reprocess`).
- **Логи контейнеров** — драйвер `json-file` без лимита.
- **Образы приложения** — каждый деплой ~1 ГБ, удалялись только старше 7 дней; при 5–10 деплоях в день это десятки гигабайт.
- **Память** — лимитов нет ни у одного контейнера, у Redis нет `maxmemory`, Postgres на настройках по умолчанию.

Рассматривали ClickHouse — отклонено: объём фактов — единицы миллионов строк в год, Postgres с индексами отвечает за миллисекунды; диск занимают файлы, а не база; ClickHouse сам требует 2–4 ГБ памяти, которых на сервере нет.

## Решение

1. **Сырьё:** на локальном диске хранится в gzip (`<key>.gz`, ключи для кода не меняются; несжатые старые файлы читаются и сжимаются). Ночная джоба `raw:prune` (05:30 UTC): у дней старше 7 дней (после окна ночного пересчёта) оставляет только последний прогон, всё старше 90 дней (окно `geo:reprocess`) удаляет. Владелец просил «удалять старше 30 дней»; 90 выбрано, чтобы не сломать пересчёт гео после сопоставления страны, а дедупликация убирает основную массу уже с 7-го дня.
2. **Логи:** 3 × 20 МБ на контейнер.
3. **Образы:** `deploy/prune-images.sh` держит 3 последних задеплоенных образа (текущий + 2 для отката), остальные теги приложения удаляет.
4. **Память:** Postgres 2 ГБ (`shared_buffers=512MB`, `effective_cache_size=2GB`, `work_mem=16MB`), воркер 1,5 ГБ (куча Node 1152 МБ), web 1 ГБ (768 МБ), Redis 384 МБ (`maxmemory 256mb`, политика `noeviction` обязательна для BullMQ), Caddy 128 МБ. Около 3 ГБ остаётся ОС и кешу файлов. Очередь хранит выполненные задачи не больше 100 и 7 дней, упавшие — 200 и 30 дней.

## Последствия

- Пересчёт из сырья старше 90 дней невозможен — такие дни перезапрашиваются бэкфиллом.
- Контейнер, упёршийся в лимит, перезапускается (`restart: unless-stopped`) вместо того, чтобы выдавить остальных; воркер продолжает очередь с места остановки.
- Первый деплой с этими настройками пересоздаёт контейнеры — старые логи удаляются вместе с ними.
- Тесты: unit `rawKeysToDelete`, gzip-хранилище и `pruneRaw`; int — джоба `raw:prune` в расписании и в `IngestRun`; ci — `prune-images.test.sh`; CI проверяет compose через `docker compose config`.
