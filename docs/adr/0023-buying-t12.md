# ADR 0023. Отчёт «Окупаемость закупки» (бывш. «Закупка T1/T2»): форматы × тиры через фильтры ADOK

Статус: принято · 2026-11-25

## Контекст

Владелец хочет понимать, можно ли поднять бид в закупке трафика на T1/T2, чтобы нарастить объём (первый случай — hentaismile.com). Условие владельца: считать **только попсы и только T1/T2** и сопоставлять их с расходами. Все данные — из AdSpyglass (ADOK).

Чего не хватало:
- **Попсы × страна.** ADOK отвечает 422 на два `group_by`. Поэтому есть только «сайт × страна» (`FactRevenueGeo`) и «сайт × формат» (`FactRevenueFormat`).
- **Расход × страна.** Расход по ревшаре считается по источнику (`FactTrafficSource` × `revShare`, ADR 0006), без страны. `v_site_geo_alloc_daily` раскладывает его по странам пропорционально выручке. Значит, отношение «расход / выручка» во всех странах одинаково, и для решения о биде этот разрез бесполезен.

## Решение

- **Одно измерение плюс фильтр вместо двух измерений.** Фильтр по сайту ADOK понимает (`platforms_ids[]`), значит, принимает и другие фильтры. Два новых разреза в плане запросов (ADR 0016), по одному запросу на сайт в день:
  - **«Попсы по странам»** (`popunder_geo`): `group_by=country` с фильтром по зонам попсов сайта → `FactRevenueFormatGeo` (дата × сайт × формат × страна);
  - **«Источники на T1/T2»** (`source_t12`): `group_by=traffic_source` с фильтром по странам тиров 1 и 2 → `FactTrafficSourceTier` (дата × сайт × источник × `T12`).
- **Имена фильтров подбираются проверкой.** Документирован только `platforms_ids[]` (из веб-интерфейса). Кнопка «Проверить фильтры ADOK» на `/buying` пробует кандидатов на одном дне выбранного сайта, примерно 10 запросов в общем бюджете и с общей паузой:
  - зоны: `spots_ids[]`, `spot_ids[]` (ID зон), `ad_types[]`, `ad_types_ids[]` (`popunder`);
  - страны: `countries_ids[]` (ID ADOK из ответа по странам), `countries[]`, `countries_ids[]`, `country_codes[]` (ISO).
  
  Найденные фильтры сохраняются в `AppSetting asg_buying_filters`, разрезы включаются в плане, изменение пишется в журнал. Без найденного фильтра разрез не тратит запросы.
- **Защита от проигнорированного фильтра.** Неизвестный фильтр ADOK молча игнорирует. Поэтому каждый ответ сверяется (`filters.ts`):
  - **попсы** — по своим показам. Загрузки не годятся: попс стоит почти на каждой странице, а показы баннеров его перекрывают. Показов не больше, чем у формата попсов (+10%), и меньше всего сайта;
  - **T1/T2** — по загрузкам. Они должны совпасть с загрузками T1/T2 из разреза по странам (±10%).
  
  Не прошёл — день не пишется, причина попадает в `IngestRun.error`.
- **Сторона сеток.** Как и в разрезе по странам (ADR 0005), `broker_income` под фильтром может прийти нефильтрованным:
  - выручка попсов по странам — итог формата за день (`FactRevenueFormat`), разложенный по `predicted_income` (`allocateBroker`);
  - выручка источника на T1/T2: если пришла вся выручка источника при доле загрузок меньше 90%, берётся выручка источника × его доля `predicted_income` на T1/T2.
- **Расход T1/T2** = выручка источника на T1/T2 × его `revShare`. **Купленные загрузки** — загрузки источников с `revShare > 0`.
- **Решение по биду** (`bidAdvice`, `src/lib/metrics.ts`) — всё отношениями сумм:
  - цена 1000 купленных загрузок T1/T2 сравнивается с выручкой попсов на 1000 загрузок T1/T2;
  - предел бида = попсы на 1000 × (1 − целевая маржа), по умолчанию 20%;
  - «можно поднимать» — предел выше цены больше чем на 5%; «на грани» — в пределах ±5%; «не поднимать» — ниже.
  
  История (`bidElasticity`): дни делятся по медиане цены, дорогая половина сравнивается с дешёвой — объём в день и попсы на 1000.
- **Пока разрезов нет — оценка с пометкой.** Попсы T1/T2 = выручка T1/T2 × доля попсов в выручке форматов сайта за день. Расход — по `v_site_geo_alloc_daily`. Страница показывает, сколько дней посчитано точно.

## Последствия

- План запросов растёт на 2 × сайтов × дней перечитки, когда разрезы включены (27 сайтов × 3 дня = +162 в ночь). При бюджете 800 бэкфиллу почти ничего не остаётся, поэтому разумно поставить «без лимита» или отключить ненужные разрезы.
- Прошлые дни заполняет обычный «Бэкфилл AdSpyglass» (режим «все разрезы») с выбранным сайтом.
- Если ADOK не примет ни один фильтр, отчёт остаётся на оценке. Следующий шаг — экспорт CSV «формат × страна» из веб-интерфейса ADOK (`docs/product/12-analytics-gaps.md`).
- Допущение: купленная загрузка зарабатывает как средняя загрузка T1/T2 сайта. Все форматы на 1000 загрузок показаны рядом как запас.

## Дополнение: формат × тиры по запросу, биды источников (26.11)

Владелец попросил другой порядок работы: выбрать формат (один, несколько или все), выбрать тиры — и увидеть доход на 1000, расход на 1000 и ответ, можно ли поднимать ставку. Уточнил: «Дони» — источник трафика в ADOK, покупается по биду CPM. Отчёт переименован в «Окупаемость закупки».

- **Матч дохода и расхода — по самому купленному трафику.** Раньше доход считался по сайту в среднем, а расход — по источнику: это разные множества трафика. Теперь срез — это отчёт ADOK `traffic_source` по сайту с фильтром по странам тира (загрузки и весь доход трафика каждого источника в тире) и второй такой же запрос с фильтром по зонам выбранных форматов (доход форматов). «Все форматы» обходятся без второго запроса.
- **По запросу, а не ночью.** Срезов «форматы × тиры» слишком много, чтобы тянуть каждую ночь. Кнопка «Посчитать точно в ADOK» делает запросы сразу за весь период: до двух на тир, один для таблицы стран и ещё один, если фильтр стран работает по ID ADOK, — не больше 12. Ответ хранится в `BuyingSlice` (ключ: сайт, период, форматы, тиры), повторное открытие запросов не тратит. Ночные разрезы `popunder_geo` и `source_t12` остались в плане как история по дням, проверка фильтров их больше не включает.
- **Сверки.** Ответ по тиру сверяется по загрузкам с разрезом по странам (±10%). Ответ с двумя фильтрами — по показам: не больше среза тира и не весь срез, когда формат — явная часть сайта (`formatScoped`). Тир, не прошедший сверку, берётся оценкой с пометкой. Если не прошёл только фильтр зон, тир остаётся точным, а формат берётся долей в выручке сайта.
- **Сторона сеток под фильтрами** (ADR 0005). Весь доход источника в тире — `t12Revenue`. Доход форматов внутри него — `formatRevenue`: если `broker_income` пришёл нефильтрованным, доход среза делится по доле `predicted_income` (затем показов) и не превышает среза.
- **Расход — бид источника по тиру** (`BidRate`: источник, сайт или все сайты, тир, $ за 1000 визитов, загрузок на визит, с даты). В ADOK бида нет, поэтому он вводится на странице; изменения пишутся в журнал. ADOK считает загрузки, поэтому цена 1000 загрузок = бид / загрузок на визит (`bidCostPer1kLoads`). Берётся ставка, действующая на конец периода; ставка сайта важнее общей. У источника без бида расход — его ревшара от дохода (ADR 0006); источник с ревшарой 0 бесплатный и в «платные» не входит.
- **Оценка без фильтров** (`estimateSlice`): трафик источника делится по тирам как у сайта (загрузки — по загрузкам, доход — по доходу), формат — по доле в выручке форматов (`v_format_daily`). Допущение: у источника те же гео и форматы, что у сайта в среднем. На странице это помечено.
- **«На 1000 юзеров»** показывается по тиру, только когда у сайта есть уники Метрики: доход выбранных форматов со всего трафика тира / уники × 1000. Основная единица — 1000 загрузок: её считает ADOK.
- **Не входит:** общий расход в P&L (`FactCost`) по-прежнему считается ревшарой источника. Перевод бидовых источников на биды во всём учёте — отдельная задача.

## Дополнение: одна таблица «сайт → тир → формат» (26.11, упрощение)

Владелец попросил проще: без маржи, пределов, вердиктов и «на 1000 загрузок». Нужна одна таблица — какие тиры по каким форматам на каких сайтах сколько принесли и сколько потратили за период; из показателей — доход, расход, CPM.

- **Дерево сайт → тир → формат** с колонками «Доход», «Расход», «CPM» (доход / свои показы × 1000, отношение сумм) и «Данные» (ADOK или оценка). Фильтры: сайт, тиры, форматы, период. Вердикт, KPI, целевая маржа, пределы ставки и таблица стран убраны; `bidAdvice` удалён.
- **Расход стоит на тире и сайте, у формата его нет.** Платим источнику за трафик тира целиком, а не за формат. Делить расход по форматам — значит выдумывать цифру. При фильтре по форматам доход — сумма выбранных форматов, расход — весь расход тира.
- **Срез считается на сайт целиком** (`siteSliceWith`): ключ кеша — сайт + период, выбор тиров и форматов на странице запросов не требует.
  - Доход формата по тирам: `country` с фильтром зон формата, по запросу на каждый формат сайта; выручка формата раскладывается по странам через `predicted_income` (`allocateBroker`) и сворачивается в тиры.
  - Расход по тирам: `traffic_source` с фильтром стран тира, по запросу на каждый тир с трафиком; расход = бид × загрузки или ревшара × доход источника в тире.
  - До 14 запросов на сайт. Каждая часть сверяется отдельно; не прошедшая остаётся оценкой с пометкой. Доход тира целиком всегда точный — он из разреза по странам.
- **Все сайты** — фоновая задача `asg:buying` в очереди ADOK: считает срезы по очереди, сайт без точных данных попадает в `IngestRun.error`, пауза или бюджет ADOK останавливают прогон. На странице — «точно посчитано X из Y сайтов».
- **Оценка** до расчёта: доход тира × доля формата в выручке форматов сайта; загрузки и доход источника × доля тира.
