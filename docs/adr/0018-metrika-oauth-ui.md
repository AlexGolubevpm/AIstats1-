# ADR 0018. Метрика подключается из интерфейса по OAuth; её секреты лежат в базе зашифрованными ключом сервера

Дата: 2026-10-09. Статус: принято.

## Контекст

До этого Метрика работала только через `METRIKA_TOKEN` в `.env`, который владелец должен был положить в секреты GitHub и прогнать `Sync server .env`; счётчик каждого сайта вводился руками. Правило ADR/08-backend: «секреты интеграций — только в `.env`, в базу не пишутся». Владелец завёл OAuth-приложение в Яндексе и попросил подключение из интерфейса с автоматической привязкой счётчиков к нашим сайтам (чужие не заводить).

OAuth-токен выдаёт Яндекс в момент подключения — через `.env` и CI он пройти не может без ручной работы. Сайт пока открыт по HTTP без домена в переменных, Redirect URI приложения неизвестен, поэтому callback-маршрут сейчас невозможен.

## Решение

1. **Поток без callback.** Владелец сохраняет ID и секрет приложения в блоке «Яндекс Метрика» на `/settings/integrations`, открывает `oauth.yandex.ru/authorize?response_type=code&client_id=…`, Яндекс показывает код подтверждения на `oauth.yandex.ru/verification_code`, код вставляется в форму, сервер меняет его на access + refresh токен (`POST /token`, Basic-auth приложения).
2. **Хранение.** `AppSetting` ключ `metrika_oauth`: `clientId` открыто (он и так в ссылке), секрет приложения, access- и refresh-токены — AES-256-GCM (`src/server/crypto.ts`) ключом `APP_SECRET`, который `deploy/apply-env.sh` генерирует на сервере один раз и не перезаписывает. Дамп базы без `.env` токенов не раскрывает; `mcp_reader` таблицу не читает; интерфейс секреты не показывает. Смена ключа → блок сообщает «подключите заново».
3. **Приоритет токенов.** `metrikaToken()`: подключение из UI → иначе `METRIKA_TOKEN` из `.env`. Старый путь остаётся рабочим; `configuredSources` учитывает оба.
4. **Счётчики по доменам.** `GET /management/v1/counters?field=mirrors`; `matchCounters` сопоставляет активные счётчики с нашими сайтами по `normalizeDomain` (сайт, зеркала, `www.`). Пишется только однозначное совпадение в пустое поле (`AuditLog`); конфликты и неоднозначности показываются и решаются руками на `/settings/sites`; счётчики без нашего сайта не заводятся.
5. **Обновление.** Refresh за 30 дней до истечения в почасовом джобе `metrika`; неудача попадает в `IngestRun.error`, ингест идёт старым токеном.

## Альтернативы

- **Секреты GitHub + `Sync server .env`** (как раньше) — токен всё равно надо получать в браузере и переносить руками; владелец уже откладывал этот шаг; не решает привязку счётчиков.
- **Открытое хранение в базе** — проще, но дамп базы раскрыл бы токен; шифрование ключом из `.env` стоит ~40 строк.
- **Callback-маршрут `/api/metrika/oauth/callback`** — удобнее, но требует зарегистрированный Redirect URI на https-домене. Следующий шаг после переезда на `xhubtraffic.com/admin`.

## Последствия

- Правило «секреты только в `.env`» уточнено: секреты, которые вводит владелец в интерфейсе, лежат в базе зашифрованными ключом сервера; ключ — часть бэкапа сервера.
- `deploy/apply-env.sh` стал обязательным для каждого деплоя (создаёт `APP_SECRET`); локально/в тестах ключ задаётся переменной.
- Новые тесты: unit (шифрование, OAuth-клиент, сопоставление), int (подключение, приоритет токенов, обновление, применение счётчиков), CI (`apply-env.test.sh`), E2E (блок на интеграциях).
