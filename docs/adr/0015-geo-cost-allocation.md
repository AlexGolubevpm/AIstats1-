# 0015. Расход по странам: ставка — по загрузкам, revshare — по выручке; одна раскладка во вьюхе

- Статус: принято; уточняет [ADR 0008](0008-forecast-and-geo-cost-allocation.md) (раздел «Гео»)
- Дата: 2026-10-08

## Контекст

Алерт «Убыточное гео IN на japan-whores.com» показывал расход $104 при выручке $56, а матрица `/geo` по тому же сайту — положительный ROMI по всем странам. Две причины.

1. Раскладка расхода без страны (`ZZ`) была написана дважды: в SQL алерта (по дням, только дни с разрезом по странам) и в TypeScript страниц (`spreadNoCountry`: за период, причём вместе с выручкой `ZZ` — а это дни бэкфилла «только итоги» без стран). Индия с большой долей загрузок получала кусок чужой выручки на странице и не получала его в алерте.
2. ADR 0008 выбрал «по загрузкам» для ставочного расхода (CPU/CPM: платим за трафик). Но основной расход сейчас — revshare из ADOK (`origin = ASG`): источнику уходит доля **выручки, которую принёс его трафик**. Такой расход пропорционален выручке по определению. Раскладка по загрузкам приписывала дешёвым по CPM гео расход, которого там нет, — отсюда 20 ложных «убыточных гео».

## Решение

1. `v_site_geo_daily` делит расход по природе: `cost_rate` (RATE, IMPORT) и `cost_revshare` (ASG).
2. Новая вьюха `v_site_geo_alloc_daily` — единственная раскладка: за каждый день и сайт `ZZ`-ставка уходит на страны дня пропорционально загрузкам, `ZZ`-revshare — пропорционально выручке страны (без весов — поровну); `XX` долей не получает; строки с долей помечены `estimated`. День без разреза по странам оставляет всё на `ZZ`; строка `ZZ` сохраняет свою выручку, загрузки и Метрику (расход 0, если он разложен). Деньги только перемещаются: суммы по сайту равны `v_site_geo_daily`.
3. Алерт `lossGeo`, `geoTable`, `geoMatrix`, гео-строки гипотез читают эту вьюху. `spreadNoCountry` удалён. Выручка без страны по странам больше не раскладывается — показывается строкой «Без страны» без ROMI.
4. Следствие, которое надо понимать: при чисто revshare-закупке ни одна страна не «убыточна сама по себе» — её ROMI равен ROMI сайта. Алерт «Убыточное гео» теперь срабатывает только там, где есть ставочный расход (за уника, 1000 загрузок, импорт) или расход, заведённый прямо на страну. Это честно: без выгрузки ADOK «источник × страна» другого ответа нет ([12 → пробелы](../product/12-analytics-gaps.md)).

## Альтернативы

- **Оставить две реализации и «синхронизировать».** Они уже разошлись один раз; одна SQL-вьюха дешевле.
- **Раскладывать весь расход по выручке.** Ставочный расход действительно платится за трафик; его раскладка по загрузкам остаётся (ADR 0008).
- **Раскладывать `ZZ`-выручку по загрузкам (как было).** Выручка на загрузку у стран отличается в разы; это не оценка, а шум, который к тому же маскирует убытки.

## Последствия

- Активные ложные алерты закрываются на следующем прогоне (кандидатов не будет).
- В MCP (`query`) вьюха доступна; `estimated` отличает оценку от факта.
