# 0014. Базовый путь приложения — параметр сборки; домен целиком на нашем VPS

- Статус: принято
- Дата: 2026-10-08

## Контекст

Владелец хочет открыть дашборд по адресу `https://xhubtraffic.com/admin`. Домен пустой: девопсы меняют только A-записи на IP нашего VPS. DNS направляет на сервер весь домен, а не путь, поэтому «/admin» — настройка приложения и прокси. Next.js фиксирует `basePath` при сборке; почти всё в приложении (`<Link>`, `redirect()`, `revalidatePath()`, middleware, ссылки из БД) префиксуется им автоматически, вручную — plain `<a href>`, путь куки и URL, которые показываем людям.

## Решение

1. `BASE_PATH` — аргумент сборки образа (`Dockerfile`, `next.config.ts`: `basePath` + `NEXT_PUBLIC_BASE_PATH`). Образ для `/admin` и образ для корня разные; CI берёт значение из переменной репозитория `APP_BASE_PATH`. E2E гоняются на корневой сборке — базовый путь проверяется юнит-тестом хелпера и ручной сборкой.
2. `src/lib/base-path.ts`: `withBase()` для plain-ссылок и MCP-URL, `cookiePath()` для куки сессии (куки не уходит на остальной домен).
3. Деплой пишет адрес в `.env` сам (`deploy/apply-env.sh` из переменных `APP_DOMAIN`, `APP_BASE_PATH`): `APP_DOMAIN`, `BASE_PATH`, `CADDYFILE`, `COOKIE_SECURE`, `APP_URL`. Два Caddyfile: обычный и `Caddyfile.basepath` (корень → редирект на приложение, `robots.txt` закрыт, остальное 404). Пустые переменные — поведение как раньше.
4. TLS терминирует Caddy на VPS, где и DNS: никаких внешних прокси и `X-Forwarded-Host`, которые ломают проверку Origin у server actions.

## Альтернативы

- **Поддомен `admin.xhubtraffic.com`.** Проще (ноль правок кода), но владелец просил путь. Остаётся запасным: `APP_DOMAIN=admin.xhubtraffic.com`, `APP_BASE_PATH` пустой.
- **Срезать префикс в Caddy (`handle_path`) и оставить приложение в корне.** Все ссылки приложения вели бы на `xhubtraffic.com/sites/…` мимо `/admin`.
- **Базовый путь во время выполнения.** Next так не умеет: клиентские чанки и ссылки собираются с путём внутри.
